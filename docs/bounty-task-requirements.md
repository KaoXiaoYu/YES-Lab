# 悬赏任务 · 需求清单（已确认）

> 本文是悬赏任务**本体**的需求清单，供逐条审核。
> **到期冻结与到期结算的通用规则不在本文**——它们对三类任务统一，见 [`docs/task-settlement-requirements.md`](task-settlement-requirements.md)；技术设计见 [`docs/bounty-task-design.md`](bounty-task-design.md)。
> 状态说明：悬赏本体与奖金履约台账已实现；悬赏 API 回归、前端检查及本地管理/成员页浏览器检查通过。上线验收仍待 `V14`—`V16` 预生产 MySQL 演练、InnoDB 并发接取验证、规定尺寸截图与部署后业务复核。

## 1. 目标与范围

在现有任务模块上新增第三类任务「悬赏任务」：

1. **奖励分两层，互相独立**
   - **奖金**：线下现金/实物奖励，系统登记**一段统一说明**（如「500 元现金 + 获奖证书」），不逐人区分金额、不做线上支付。逐获奖者记录待发放、已发放、已领取状态与操作留痕。奖金有 **m 份**，**最先完成的 m 人获得**。
   - **积分**：可选绑定，**任务到期后统一结算**——结算时状态为「已完成」的人获得积分。通用结算规则见 `docs/task-settlement-requirements.md`。
2. **接取人数可设上限也可不限**：限制时最多 n 人接取、先到先得；不限制时来多少人都能接。接取上限与奖金份数 m 是两个独立设置。
3. **提交即完成**：接取者在截止前提交完成说明的那一刻就算完成，没有「待确认 → 管理员审核」环节；管理员只做事后复核。
4. **驳回后奖金顺延**：奖金资格按完成名次分配；某位获奖者被驳回后，奖金自动顺延给名次最靠前的未获奖完成者。
5. **到期冻结**：到期后不能再接取、提交、驳回（与全站口径一致，见结算需求清单）。

## 2. 需求清单

### A. 任务类型与奖励

| 编号 | 需求                                                                                                                 | 验收方式                     |
| ---- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| A1   | 新增第三类任务 `BOUNTY`（悬赏），与 `ONBOARDING` / `STANDARD` 并列，共用大任务、子任务、富文本与提交这套结构         | 创建类型为悬赏的任务成功     |
| A2   | 悬赏的奖励由**奖金**与**积分**两部分组成，两者互相独立、**至少存在一种**                                             | 两者都为空时保存/发布被拒    |
| A3   | 奖金用 `prize_description`（≤500 字，纯文本）登记**一段统一说明**，所有份数内容相同；不逐人区分金额、无支付/报销流程 | 悬赏详情与成员端可见奖金说明 |
| A4   | 奖金份数 `prize_slots = m`（1—100）表示**最先完成的 m 人**获得奖金；为空表示不设奖金                                 | 第 m+1 名完成者不获奖        |
| A5   | 奖金说明与奖金份数必须**同时填写或同时为空**                                                                         | 只填一项时被拒               |
| A6   | 积分用现有 `tasks.points` 字段承载（0—100000）：大于 0 表示绑定积分，等于 0 表示不绑积分                             | 绑定后到期结算产生积分流水   |
| A7   | 悬赏沿用富文本正文、可选的单层子任务（0—50 条）、起止日期；不设时长字段                                              | 与普通任务表单能力一致       |

### B. 接取与名额

| 编号 | 需求                                                                                                               | 验收方式                     |
| ---- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| B1   | 成员在「悬赏榜」看到可接取的悬赏：标题、奖金说明与份数、已产生份数、接取人数（不限或 `x / n`）、截止日期、本人状态 | 页面可用                     |
| B2   | 成员点「接取」即参与该悬赏，对象状态为 `PENDING`（进行中），来源记为 `CLAIM`                                       | 接取后榜单与我的任务同时可见 |
| B3   | **接取人数上限可选**：`headcount_limit` 为空表示不限人数；非空表示最多 n 人接取、先到先得                          | 两种配置都能创建并生效       |
| B4   | 设了上限时**接满即止**：第 n+1 人接取返回明确错误（409），界面禁用接取并说明原因                                   | 超出上限无法接取             |
| B5   | 接取必须原子：并发争抢最后一个接取名额时只能有一人成功，不允许超发                                                 | 并发用例只有一人成功         |
| B6   | **同一人对同一条悬赏只能接取一次**：放弃后、被移除后、被驳回后都不能再接                                           | 第二次接取一律被拒           |
| B7   | 接取窗口：任务已发布、且今天在 `[start_date, end_date]` 之内（日期为空表示不限）；未开始或已过截止日期不能接取     | 窗口外接取被拒               |
| B8   | 接取者**未完成且未截止前可自行放弃**：`PENDING → ABANDONED`，占用名额归还（若设了上限），本人不可再接              | 放弃后他人可接、本人不可再接 |
| B9   | 管理员可**移除**接取者以释放名额（`PENDING → ABANDONED`，与本人放弃同口径）；到期后仍可移除（清理动作）            | 名额归还                     |
| B10  | 接取名额招满**不自动结束任务**，只做显示层标记；何时结束由管理员决定                                               | 无自动状态变更               |

### C. 完成、名次与奖金分配

| 编号 | 需求                                                                                                                                        | 验收方式                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| C1   | **提交即完成**：接取者在截止前提交完成说明后对象直接进入 `APPROVED`，不需要管理员审核，**此时不发积分**（积分走到期结算）                   | 状态为已完成、无积分流水      |
| C2   | 悬赏**不使用 `SUBMITTED`（待确认）状态**；该状态继续保留给普通任务与新手任务                                                                | 悬赏对象不会出现待确认        |
| C3   | 完成时**锁定完成名次** `completion_rank`（第几个完成，从 1 开始）；名次一经分配不再重算                                                     | 名次连续、唯一、不重复        |
| C4   | **奖金按完成名次分配**：奖金持有者 = 当前已完成对象中名次最靠前的 `min(m, 已完成人数)` 位                                                   | 完成人数不足 m 时全部获奖     |
| C5   | **驳回后自动顺延**：某位奖金持有者被驳回后，奖金自动由名次最靠前的未获奖完成者接手；暂时无人可接则份额空置，等下一个完成者自动获得          | 第 2 名被驳回后奖金落到下一位 |
| C6   | 顺延产生的新奖金持有者收到站内消息（说明是顺延所得）                                                                                        | 成员收到通知                  |
| C7   | 待发放奖金资格被驳回后转为已撤销并顺延；已登记线下发放或领取的奖金不可再驳回（409），名次不重算                                             | 发放后驳回被拒且履约留痕保留  |
| C8   | 奖金份额发完后仍可继续接取与完成：后续完成者只能指望积分（若绑定），不再获奖                                                                | 第 m+1 名完成者无奖金         |
| C9   | 悬赏**不强制勾完全部子任务**即可提交（子任务只作清单展示，与普通任务一致）                                                                  | 未勾完子任务也能提交          |
| C10  | 已完成（`APPROVED`）后不能再重复提交或修改完成说明                                                                                          | 重复提交被拒                  |
| C11  | 管理员**事后复核**可驳回：`APPROVED → REJECTED`，必填意见，占用名额归还，触发奖金顺延，发通知；**只允许在任务到期前**（到期后驳回返回 409） | 到期后驳回被拒                |
| C12  | 已驳回是终态，任务模块不提供「撤销驳回」；更正走管理员重新发布一条悬赏                                                                      | 无撤销入口                    |
| C13  | **奖金资格与积分资格独立**：试用成员、教师可以拿到奖金（线下奖励不受积分规则约束），积分按积分模块规则跳过/不发                             | 试用成员获奖但无积分流水      |
| C14  | 每位当前奖金持有者单独跟踪线下发放状态 `待发放 → 已发放 → 已领取`，记录操作者与时间；历史获奖记录不覆盖                                     | 名单与成员任务页可查状态      |
| C15  | 管理员登记发放后，只有该获奖者本人可以确认领取；两项动作分别留痕                                                                            | 他人无法代确认，操作留有时间  |
| C16  | 在发放前驳回当前获奖者时将该台账标记为已撤销并保留历史；已经登记发放或领取的奖金不可再驳回，接口返回 409                                    | 发放后驳回被拒且原记录可查    |
| C17  | 发放与领取是线下履约记录，可在任务截止/结束后继续登记；不得改变完成名次、奖金资格或积分结算                                                 | 结束后仍可登记且积分不变      |

## 4. 明确不做

- 逐人奖金金额登记、每份奖金内容不同（分名次奖励）、线上支付 / 报销
- 成团 / 组队悬赏；抽签、优先级队列、名额超发、候补队列、预留份额中间态
- 自动分配接取者、满员自动结束、奖金发完自动结束、到期自动作废
- 悬赏对象二次接取（放弃后重新接取、接取冷却期）
- 「撤销驳回」与自动反向积分
- 顺延之外的重新排名（名次一经分配不再重算）
- 悬赏多版本 / 灰度 / 模板 / 周期悬赏
- 附件上传、任务评论 / 讨论区、悬赏与项目或竞赛关联
- 悬赏专属的结算实现（结算由全站统一的结算服务处理）

## 5. 已确认口径

| 编号 | 事项                                       | 默认结论                                                                             |
| ---- | ------------------------------------------ | ------------------------------------------------------------------------------------ |
| Q1   | 接取人数上限与奖金份数的关系               | 设了接取上限时要求 `m ≤ n`                                                           |
| Q2   | 管理员移除接取者后，该成员能否重新接取     | 不能，与本人放弃同口径                                                               |
| Q3   | 是否强制勾完全部子任务才能提交             | 不强制，子任务只作清单（与普通任务一致）                                             |
| Q4   | 悬赏是否复用等级条件限制接取资格           | 复用 `task_audience_rules`；条件为空表示全体成员可接                                 |
| Q5   | 教师能否接取悬赏                           | 能接能获奖，但结算时积分跳过（教师不参与成员积分统计）                               |
| Q6   | 延长截止日期后已结算任务的补结算           | 由结算服务的通用规则处理（重置结算标记，只补发新增）                                 |
| Q7   | 发放登记后是否仍允许管理员驳回该获奖者     | 不允许：线下发出后无法由系统收回，驳回接口返回 409；发放登记前仍可驳回并按原规则顺延 |
