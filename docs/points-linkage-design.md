# 积分管理联动与首页同步技术设计

> 2026-10-03，已审核，代码与本地验收完成。依据 [需求清单](points-linkage-requirements.md)，需求优先。成员范围及首页三个周期榜已由用户确认。

## 1. 改造前的现状结论

- `PublicShowcaseService.getHome/getRanking` 使用 `InMemoryPublicShowcaseRepository` 的演示榜单。
- `publicApi.normalizeHome` 把榜单转换成分数数组；`PublicHomeView.rankings` 按 `members` 下标取分，丢失真实身份与名次。
- `PointService` 已维护成员总分、账本、自然周期榜、封顶及反向流水，可抽出共用统计逻辑。
- `GrantRequest` 强制 `sourceReference/evidenceUrl`；`PointGrantEntity` 无项目/竞赛来源字段。`AdminPointsView` 可选所有符合资格的成员。
- 项目有负责人及成员集合；竞赛有队长、参赛者及可空的本站成员关联，可据此计算发放候选，不按姓名匹配。

## 2. 数据与兼容

新增 `V20__point_grant_sources.sql`（施工前再次确认版本未被占用），不修改 V1—V19。生产应用状态以 `flyway_schema_history` 为准；既有脚本引入历史只读核对。

| 字段                            | 用途与约束                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------- |
| `competition_id` / `project_id` | 可空 BINARY(16) 来源外键，一笔最多一种关联；新增手工竞赛/项目事项必须对应一项 |
| `source_entity_reference`       | 可空来源原始 UUID 文本快照，删除来源后仍保留身份                              |
| `source_name`                   | 可空来源名称快照，用于历史展示                                                |
| `request_key`                   | 可空 BINARY(16) 请求幂等键及唯一索引；历史和系统任务路径可空                  |

来源外键使用 `ON DELETE SET NULL`，避免凭新增关联改变既有删除流程；审计依靠原始 ID、名称和事项快照。服务端校验互斥与类型，不依赖页面。关联记录读取/锁定先于按 ID 排序锁成员，以稳定锁顺序处理来源删除/变更并发。

继续使用 `source_reference` 展示积分编号。新增手工发放编号格式为 `PTS-YYYYMMDDHHmmssSSS-<UUID>`，以服务器北京时间生成；撤销生成独立编号并保留原批关联。长度符合已有 190 字符与唯一约束。系统任务沿用确定性来源编号，历史编号不改写。

`evidence_url` 暂保留原有非空列，新手工记录写空字符串，取消手工 API 对凭证的必填要求与 URL 校验。这样不删除历史证据，也不需要重写旧表字段；用户界面不展示凭证；响应暂保留历史凭证字段以兼容系统任务现有接口。竞赛成果库证书不受影响。

另增加可空 `request_fingerprint VARCHAR(64)` 保存规范化请求摘要，用于校验同键不同参数。新增字段均可空，既有行原样保留；迁移使用 MySQL `information_schema` 判断列、索引与外键缺失后补齐。JPA/H2 自动建表仅覆盖业务测试，不能证明 SQL 可用。

## 3. 管理 API 与发放事务

- 新增积分管理来源候选接口，由 `POINTS_MANAGE` 授权，返回必要的来源 ID、名称、竞赛奖项/状态和符合资格的关联成员摘要，不依赖公开库列表，也不暴露证书内容。
- 手工发放请求增加可选 `competitionId/projectId` 和必填 `requestKey`；不再接收管理员填写的编号/凭证。其他原字段及校验保留。
- `COMPETITION_AWARD` 要求竞赛 ID 且无项目 ID；`PROJECT_TASK` 要求项目 ID 且无竞赛 ID；其他子类型不接受来源 ID。竞赛要求 FINISHED、审核通过、已填写奖项，已确认。
- 项目候选为负责人及成员集合；竞赛候选为队长及绑定本站档案的参赛者，去重后套用原正式学生/非教师/非本人条件。
- 保存时重新读取来源状态和成员关系并检查所有接收人；候选加载后变更导致不再符合条件时，整批拒绝，前端保留输入并提示刷新候选。
- 发放内部仍复用现有分配、封顶、锁成员、余额更新、流水与通知。来源校验只放在管理员手工入口，避免系统任务 `PROJECT_TASK` 被错误强制绑定项目。
- 表单首次提交生成 `requestKey`；未确认结果的重试复用该键。后端相同键且相同规范化业务参数返回已有批次，不更新余额或通知；相同键不同参数返回冲突。比较原申请分值而非封顶后分值，并使用来源 ID 快照而非可变名称。
- 并发首次提交由唯一索引兜底，冲突后的已有批次读取在有效的新事务中完成，不能在已失败事务中继续查询。撤销保留现有原批次唯一约束；来源关联与快照复制到反向批次。
- 同一来源的不同事项允许使用不同键发放；请求幂等不等于“一项目一生只能发一次”。

## 4. 首页真实榜单

抽出 PointService 中无认证依赖的共用积分统计方法，共享现行成员资格、总分读取、北京时间周期、账本聚合、排序和同分名次。站内排行榜保留原授权与本人标记；公开服务返回单独的安全投影，避免绕过现有受保护方法。

公开首页与 `/api/v1/public/rankings` 均从共用统计方法取总/月/年榜。公开返回成员 ID、姓名、首字、已公开能力标签、分值和名次；前端记录成功读取时间用于刷新反馈；不返回账号名、内部编号、联系方式或本人状态。参榜范围沿用站内正式学生口径，首页核心成员展示筛选不改变榜单集合。

前端完整保留各榜条目，直接渲染条目的成员 ID、分值与 `rank`，不再把分数数组拼到独立成员列表。链接用真实成员 ID，保持现有公开详情权限；无可用主页时只展示姓名。初始化及请求失败时展示明确状态，不使用演示榜作为积分兜底。

首页按北京时间每天零点同步，后台页面跨日后恢复前台时补刷新；请求序号防止旧响应覆盖新榜，卸载清理计时器。已存在榜单遇暂时失败可保留上次成功结果并显示更新时间/刷新失败，首次失败显示失败态；空成员集合显示空态。

## 5. 表单与流水

`AdminPointsView` 按需求顺序组织字段。项目/竞赛采用可搜索来源选择，选中后展示关联候选。切换类型/来源清空分配，保留无关的说明输入；异步加载使用请求序号防止旧来源候选覆盖新选择。保存期间禁用表单，失败保留输入并聚焦错误摘要。

事项名称可回填来源名称与奖项后编辑；来源名称单独显示，保证说明和关联不混淆。积分编号仅在成功反馈/流水中读取服务端结果。去掉新增、撤销、流水凭证控件及文案；保留贡献描述、封顶提示、撤销原因与原始记录。

使用 `ui-ux-pro-max` 的 `dependent select validation --domain ux` 命中行内校验、稳定布局、可聚焦错误摘要；Vue 查询 `forms --stack vue` 命中 `v-model` 修饰符。沿用现有组件及校验方式，不为本轮新增表单库。首页遵循 `pages/public-home.md`，其他页面遵循 MASTER；视觉规范未改变。
